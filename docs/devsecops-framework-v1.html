DevSecOpsフレームワーク設計書 v1（図解版）

GitHub Enterprise Cloud前提／1,000ユーザー以上・1,000リポジトリ以上
作成基準日：2026年11月25日 図解版：2026年11月26日 上位文書：GitHub Copilot AIガバナンス設計書 v3.1（1.4） 対象：GHEC（EMU）／GHESは対象外
結論

次の構成を推奨します。

  • Enterpriseレベルで強制する：Actionsポリシー（許可リスト＋SHAピン留め強制）とworkflow execution protections（実行保護）で、「何が・誰によって・何を使って実行されるか」を技術的に強制します。
  • 検査は中央から配る：検査ロジックは中央のDevSecOpsリポジトリが再利用ワークフローとして配布します。カスタムプロパティで対象を絞った「Require workflows to pass」ルールセットで、全リポジトリに必須化します。

この骨格はGHASの有無にかかわらず同じです。違うのは検査エンジンだけで、CodeQL／secret scanningを使うか、OSS（Semgrep・gitleaks・OSV-Scannerなど）を使うかを選びます。

1強制の柱は3つ

①2025-08に追加されたSHAピン留め必須と!によるブロック、②2026-09にGAした実行保護、③2026-10にGAしたworkflow lockfile。この3つで、tj-actions（2025年3月）やtrivy-action（2026年3月）のような「タグ書き換え」型の攻撃を構造的に防ぎます。

2GHASなしの最大の穴

privateリポジトリでは、GHASなしだとdependency reviewが使えません。依存関係はOSV-Scanner、シークレットはgitleaks、SASTはSemgrepで代替します。SBOM、Dependabot、Artifact attestations、immutable releasesはGHASなしでも使えます。

3監査→強制の段階導入

Evaluate（監査）モードから強制に移ります。高criticalityのリポジトリから始め、約2四半期で全リポジトリに広げます。scoped secrets、Data Stream、egress firewallは未GAのため「将来の置換候補」とし、本書ではインターフェースだけを定義します。

図1全体像：Enterpriseで強制し、中央リポジトリから配り、カスタムプロパティで振り分ける
上の層（Enterprise）が「実行してよいもの」を決め、中央リポジトリが「検査の中身」を配り、カスタムプロパティが「どのリポジトリに何を適用するか」を決めます。下段の3つは、隣接する取り組みや外部とのインターフェースです。

1目的・範囲・前提

1.1 目的

AIの有無にかかわらず必要なソフトウェアサプライチェーン対策を、1,000以上のリポジトリに一律に適用します。対象は、Actionsの許可リスト・SHAピン留め、GITHUB_TOKENの権限、OIDC、Dependabot、SBOM、Artifact attestations、CIでの依存関係・シークレット・SAST検査です。標準・テンプレート・再利用ワークフローを1か所（DevSecOpsリポジトリ）に集約し、少人数のプラットフォームチームで運用できるようにします。

1.3 前提（AIガバナンス設計書 v3.1と整合）

  • EMU、Entra IDによるOIDC SSO、IP許可リスト、監査ログのSIEMストリーミングが導入済み。
  • リポジトリの可視性は、数名の管理者を除きprivateのみ。
  • Enterpriseルールセット（デフォルトブランチ）を適用済み：削除禁止、force push禁止、PR必須（承認1名以上、Code Ownerレビュー必須、古い承認の破棄）、ステータスチェック必須。
  • カスタムプロパティ data_classification、copilot_agent_allowed、criticality が定義済み。本書では devsecops_tier を追加する（→4.3）。
  • GHAS（Secret Protection／Code Security）は未導入の可能性があるため、全設定で「GHASあり／なし」を併記する。
  • 運用方針：申請・例外処理を最小化し、ユーザー責任の「標準」を中心に据える。技術で強制できるものは強制する。

3設計原則

P1
強制はEnterprise、標準はリポジトリ
技術で強制できるもの（ポリシー・ルールセット）はEnterprise／Orgに置き、例外申請を最小にする。
P2
中央配布・SHA参照
検査ロジックはDevSecOpsリポジトリの再利用ワークフローに集約する。利用側はSHA（またはlockfile）で参照する。
P3
対象はカスタムプロパティで絞る
リポジトリ名の列挙は禁止。criticality・data_classification・devsecops_tierで対象を決める。
P4
監査 → 強制
Evaluateモードや監査期間を経てから強制し、移行コストを下げる。
P5
長期シークレットを置かない
クラウド認証はOIDCのみ。シークレットはenvironmentsに限定する。
P6
GHASに依存しない最低線
GHASなしでも、同等の「検出 → PRブロック」が成立するようにする。

4.1 Actionsポリシー

設定推奨値理由GHAS確度
許可するアクションEnterpriseで「Enterprise内のアクション＋選択した外部アクション」。外部はGitHub作成のものと許可リスト（policies/allowed-actions.yml で管理）のみ。Marketplaceのverified creatorの一括許可はしない2025〜2026年の主要インシデントは、いずれも外部アクション経由不要公式

SHAピン留め必須Enterpriseで「フルSHAへのピン留め必須」をON（フェーズ2以降）タグ書き換えへの対策。GitHub作成のアクションや、composite内のネストした参照も対象になり、ピン留めしていないワークフローは失敗する不要公式（ネストの挙動は二次）
Workflow lockfile中央リポジトリと高criticalityのリポジトリから導入。「Require lockfile」ポリシーはEvaluateで開始推移的依存（例：trivy-action → setup-trivy）まで固定できる。reusable workflowの呼び出しは対象外なので、別途SHAで参照する不要公式（EvaluateがGHEC限定である点は二次）
GITHUB_TOKENの既定権限read（contents: read）。各ジョブで permissions: を最小限に明示侵害時の被害範囲を限定する不要公式
ActionsによるPRの作成・承認「GitHub ActionsにPRの作成と承認を許可」をOFF（Enterpriseで固定）ボットの自己承認でレビュー必須を回避されるのを防ぐ。AIガバナンスの「人の承認」と整合不要公式
fork PRのワークフロー（private）privateリポジトリのフォークを禁止。フォークからのワークフロー実行、書き込みトークン、シークレットの送付はすべてOFFprivateが中心という前提では不要な経路不要公式
外部コラボレーターなどの承認初回コントリビューターを含め、すべての外部者に承認を求める管理者所有のpublicリポジトリ向け不要公式
アーティファクト・ログの保持90日（監査要件に応じて調整）調査できる状態を保つ不要一般

U-1DevSecOpsリポジトリの可視性（privateのみという原則との整合）複数のOrgから参照するためinternalとし、管理者例外として委員会が承認する。単一Orgで運用するなら、private＋「Org内からアクセス可」とする
U-2GHASの導入範囲Secret Protectionは全社に導入する（漏えいの事前ブロックはOSSで代替しにくいため）。Code Securityはcriticality high以上から始め、OSSとの検出差を3か月比較して判断する
U-3SHAピン留め必須とlockfileの関係当面は両方を使う。lockfileの運用が定着した後、ピン留め必須をlockfile必須に置き換えられるかをGitHubに確認する（→第15章）
U-4外部アクションのミラー運用高リスクの少数（デプロイ・クラウド認証系）だけをミラーし、それ以外はSHAで固定する
U-5CopilotクラウドエージェントのランナーGitHub-hostedを既定とし、社内資源が必要な場合だけprivate networkingのランナーを使う（Egress制御と協議）
U-6pull_request_targetを必要とする、管理者所有のpublicリポジトリワークフローファイル単位で例外を認め、checkout v7の既定動作を維持する

15GitHubへの確認事項

  1. Actionsポリシーの「SHAピン留め必須」は、lockfileに登録済みのタグ参照を適合とみなすか。
  2. 「Require lockfile」ポリシーのGA状況と、Evaluateモードの提供範囲（GHEC限定か）。
  3. scoped secrets、secretsの権限分離、Actions Data Stream、ネイティブegress firewall（GitHub-hosted larger runnersとprivate networkingへの対応を含む）の提供時期。
  4. 悪性ワークフローの承認保留を、private／internalリポジトリへ拡張する予定はあるか。
  5. Orgの .github リポジトリがprivateの場合、ワークフローテンプレートを利用できる範囲。
  6. workflow execution protectionsのアクタールールで、Copilotコーディングエージェントなどのボット主体を識別する方法。
  7. security configurationsでCode Securityを部分適用した場合の、アクティブコミッターの数え方（複数のOrgにまたがる場合）。
