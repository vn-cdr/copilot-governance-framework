# ハーネスエンジニアリング入門

## 概要

- **定義**：AIモデルの周りに作る「環境・制約・フィードバックの仕組み」を設計する分野。
- **基本式**：Agent = Model + Harness（モデルが知能、ハーネスがそれを実際に役立つ形にする）。
- **由来**：Mitchell Hashimoto氏（Terraform共同作者）が、エージェントのミスを再プロンプトではなく環境側の恒久修正で防ぐ習慣を「engineering the harness」と呼んだのが始まり。その後OpenAI・Anthropicが関連記事を公開し定着。
- **進化の流れ**：プロンプトエンジニアリング（言語）→ コンテキストエンジニアリング（情報）→ ハーネスエンジニアリング（環境）。

## instructionsはハーネスエンジニアリングか？

- instructions（システムプロンプト、CLAUDE.md、AGENTS.mdなど）は**ハーネスの構成要素の一つ**。
- ただし、文面を工夫するだけならプロンプト／コンテキストエンジニアリングの領域。
- ハーネスエンジニアリングらしくなる条件：
  - **失敗駆動で恒久化している**：ミスが起きたら追記・仕組み化して再発を防ぐ。
  - **指示だけに頼らない**：フック、CI、権限など機械的な強制と組み合わせる。

## ハーネスの主な構成要素と具体例

### 1. 指示・ルール（Instructions）

- CLAUDE.md / AGENTS.md に、ビルド・テストコマンド、コーディング規約、ディレクトリ構成を書く。
- 「やってはいけないこと」を明記する（例：`main`に直接pushしない、本番DBに接続しない）。
- エージェントが同じミスを繰り返したら、そのたびに追記して育てる。

### 2. ツール設計（Tools）

- エージェントが使えるツールを絞り、役割を明確にする（例：汎用シェルではなく「テスト実行」「PR作成」専用ツール）。
- MCPサーバーで社内システム（チケット、ドキュメント、DBの読み取り専用ビュー）に接続する。
- ツールの説明文と返り値を、モデルが誤解しにくい形に整える（エラー時に次の行動が分かるメッセージを返すなど）。

### 3. 権限・サンドボックス（Guardrails）

- ファイル書き込みやコマンド実行の許可リスト／拒否リストを設定する（例：`rm -rf`や`git push --force`を禁止）。
- コンテナや隔離環境で実行し、壊れても影響が出ないようにする。
- 認証情報は最小権限にする（例：読み取り専用トークン、特定リポジトリ限定のGitHub App）。

### 4. 検証・フィードバックループ（Verification）

- 変更後に必ずテスト・型チェック・リンターが走るようにする。
- フック（例：Claude Codeの PostToolUse）で、ファイル編集後に自動フォーマットやlintを実行し、失敗を即座にエージェントへ返す。
- CIで不合格なら差し戻し、エージェントが自分で修正するループを作る。
- 「指示で守らせる」より「機械で止める」を優先する。

### 5. コンテキスト・記憶管理（Context / Memory）

- 長いタスクでは進捗ファイル（例：`PROGRESS.md`、TODOリスト）を書かせ、セッションをまたいでも続きから再開できるようにする。
- 必要な情報だけを読み込ませる（巨大なログを丸ごと渡さず、要約や検索ツールを使わせる）。
- タスクごとにサブエージェントへ分割し、それぞれのコンテキストを小さく保つ。

### 6. オーケストレーション（Workflow）

- 「計画 → 実装 → テスト → レビュー」のように工程を分ける。
- 計画段階で人間の承認を挟んでから実装に進ませる。
- 複数エージェントの場合、受け渡し時点で出力を検証する。

### 7. 人間の承認ポイント（Human-in-the-loop）

- 不可逆・高リスクな操作だけ人間の承認を必須にする（本番デプロイ、課金発生、外部送信など）。
- 低リスク作業は自動化し、人間の確認負荷を減らす。

### 8. 可観測性・評価（Observability / Eval）

- エージェントが何を考え、どのツールを呼んだかをログに残す。
- 失敗事例を集めて評価用タスクにし、ハーネス変更の効果を測る。
- 指標の例：タスク完了率、手戻り率、PRのマージ率、トークンコスト。

## 具体例：「テストを書かずにPRを出してしまう」問題への対応

- **プロンプト的対応**：「必ずテストを書いて」と都度指示する → 次のセッションで忘れる。
- **ハーネス的対応（段階的）**
  1. CLAUDE.mdに「変更時はテスト追加必須」と追記する。
  2. PR作成前にテストとカバレッジチェックを走らせるフックを設定する。
  3. CIでカバレッジ低下を検出したら失敗させ、エージェントに結果を返す。
  4. 失敗が減ったか、ログと指標で確認する。

## 考え方のポイント

- 失敗を「モデルのせい」にせず、「環境で再発防止できないか」と考える。
- 強制力の段階：**指示（お願い）→ フック・CI（強制）→ 権限（そもそも不可能に）**。
- ハーネスは一度作って終わりではなく、失敗のたびに改善していく運用そのもの。
- 用語はまだ新しく、どこまでを「ハーネス」と呼ぶかは記事や文脈によって揺れがある。
