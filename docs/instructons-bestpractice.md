# Instructions（AGENTS.md / CLAUDE.md）のベストプラクティス

## 結論

- 正式な標準規格はないが、公式ドキュメントと実務・研究の知見が収束し、「業界の共通認識」と呼べるものはできつつある。
- 中心にある考え方は「コンテキストウィンドウは有限で、埋まるほど性能が落ちる」という制約。ほとんどの推奨はここから導かれる。

## 主な情報源

- **Anthropic公式「Best practices for Claude Code」**：もっとも信頼できる一次情報。
  - https://code.claude.com/docs/en/best-practices
- **AGENTS.md（オープン標準）**：ツール横断の共通フォーマット。2026年時点でGitHub上6万リポジトリ超が採用。
- **大規模な分析・実験**：数千リポジトリの分析ガイドや、Augment Codeによる効果測定など。
  - https://www.augmentcode.com/blog/how-to-write-good-agents-dot-md-files

## ほぼ合意されているポイント

- **短く保つ**
  - Anthropicも簡潔さを最重要視している。
  - 目安は200行以内。より厳しく150行以内とする意見もある。
- **書くべきもの**
  - 必須の環境変数など、開発環境の癖。
  - よくある落とし穴、直感に反する挙動。
  - ビルド・テスト・lintなどのコマンド。
- **書かないもの**
  - ファイルごとのコード説明（エージェントは自分で読める）。
  - 「きれいなコードを書く」「ベストプラクティスに従う」などの自明な心得。
  - READMEなど他の文書と重複する内容（リンクで参照する）。
- **コマンドを先に、文脈は後に**
  - 優れたファイルは、まず実行できるコマンドを示し、説明はその後に置く構成になっている。
- **アンチパターンを列挙する**
  - 一般論ではなく、そのプロジェクトでAIが間違えがちな具体的な事柄をリスト化する。
- **実在ファイルを例示する**
  - お手本となる実ファイルを示し、避けるべきレガシーコードも明示する。
- **失敗から育てる**
  - 最小限から始め、AIがミスするたびに追記して再発を防ぐ。
  - 実態に合わなくなった記述は定期的に削除する。
- **強制すべきルールは仕組み化する**
  - 公式の考え方は次の3つに集約される。
    1. ファイルから読み取れないことを伝える。
    2. 合否が出る検証手段（テストなど）を与える。
    3. 曲げられないルールは、指示ではなくフックや拒否ルールにする。
- **ツール間の使い分け**
  - まずAGENTS.mdを唯一の情報源として書き、AGENTS.mdで表現できない機能だけCLAUDE.mdなどに追加する。
  - Claude Codeで使う場合は、CLAUDE.md → AGENTS.md のシンボリックリンクで両対応できる。
- **大規模リポジトリでは分割する**
  - ルートのAGENTS.mdは全体ルールと案内役に留め、パッケージごとにAGENTS.mdを置く。

## 注意点（研究・実験からの知見）

- **書き方次第で逆効果になる**
  - Augment Codeの調査では、良いファイルはモデルを上位版にアップグレードしたのに相当する品質向上をもたらした。
  - 一方、悪いファイルはAGENTS.mdがない場合よりも出力を悪化させた。
- **同じファイルでもタスクによって効果が変わる**
  - 同じモジュール内で、定型的なバグ修正では評価が約25%向上し、複雑な機能追加では完成度が約30%低下した例がある。
- **プロジェクト概要はあまり効かない**
  - コードベースの概要を書いても、エージェントが関連ファイルに到達するまでのステップ数はほぼ変わらなかったという結果がある。
  - 概要を残すなら、「仕様の正は`docs/`」のようにコードから推測できないルールだけに絞る。

## 実践チェックリスト

- [ ] 200行以内に収まっているか
- [ ] コマンド（セットアップ・ビルド・テスト・lint）が冒頭にあるか
- [ ] 一般論・自明な心得を削除したか
- [ ] コードを読めば分かる説明を削除したか
- [ ] プロジェクト固有の落とし穴・アンチパターンが書かれているか
- [ ] 機械で強制できるルールは、フック・CI・権限設定に移したか
- [ ] 実態と食い違う古い記述がないか
- [ ] AIのミスを追記する運用が回っているか
