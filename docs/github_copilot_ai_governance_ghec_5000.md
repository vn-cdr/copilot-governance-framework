# GitHub Copilot AIガバナンス設計書（GHEC・5,000ユーザー／5,000リポジトリ）

-   **版**: 1.0
-   **調査基準日**: 2026-11-07
-   **対象**: GitHub Enterprise Cloud（GHEC）上の GitHub Copilot
-   **対象規模**: 約5,000ユーザー、約5,000リポジトリ
-   **前提**: GHESは利用しない。一般ユーザーは組織配下のPrivate
    Repositoryのみ利用可能。管理者は数名に限定する。
-   **目的**:
    Copilotの安全な利用を許可しつつ、情報漏えい・脆弱性混入・過剰なエージェント権限・ライセンス浪費を防ぎ、監査可能な運用を実現する。

> **重要な調査上の注記**\
> Gartnerの有料調査レポート本文は本調査で直接参照できていない。本書では、Gartnerが公開している調査概要・プレスリリース・公開記事から確認できる考え方を「Gartner公開知見」として整理し、NIST、OWASP、ISOおよびGitHub公式ドキュメントを具体的な統制設計の根拠とした。Gartnerの有料レポートに記載された詳細な成熟度モデルや推奨事項を、確認済みであるかのようには扱わない。

## 1. エグゼクティブサマリー

### 1.1 推奨方針

5,000人規模では、Copilotを単なるIDE補助機能として扱わず、**AI利用者・AI機能・データ・ツール／エージェント・生成物・開発プロセスを横断する企業統制対象**として管理する。

推奨する基本方針は次のとおり。

1.  **デフォルトは許可よりも明示的な承認**\
    新機能・Preview・新しいエージェント・MCPサーバーは、原則として管理者が評価してから段階的に許可する。
2.  **強制すべき統制はGitHubネイティブ機能で実施**\
    Enterprise／OrganizationのAI
    Controls、Copilotポリシー、リポジトリポリシー、Rulesets、Actionsポリシー、Code
    Security設定を優先する。
3.  **クライアント側のエージェント動作はEnterprise managed
    settingsで補完**\
    `.github-private`内の`copilot/managed-settings.json`を中央管理する。ただし、すべての設定がすべてのCopilotクライアントに適用されるわけではないため、設定キーごとの対応クライアントを確認する。
4.  **AIに本番変更・マージ・リリースの最終権限を与えない**\
    AI生成コードは人間がレビューし、通常のブランチ保護・CI/CD・承認を通す。
5.  **Copilotをセキュリティ検査の代替にしない**\
    CodeQL、Secret Scanning、Dependency
    Review、Dependabot、コンテナ／IaCスキャン等を継続し、Copilotの説明やレビューだけで脆弱性なしと判断しない。
6.  **ログの限界を前提に監査設計する**\
    GitHubのEnterprise監査ログはポリシー・ライセンス変更やGitHub上のAgent活動を記録するが、ローカルIDEで入力した全プロンプトを記録するものではない。必要な監査証跡は目的・プライバシー・法務要件を定めて別途設計する。
7.  **利用者教育・運用・測定を技術統制と一体化する**\
    ガイドライン、教育、例外申請、インシデント対応、利用効果測定を整備する。

## 3. Gartner公開知見から導く設計原則

### 3.1 Gartner公開情報から読み取れる方向性

Gartnerの公開調査概要「How to Mature Generative and Agentic AI
Governance for Enterprise Applications」（2025-10-29）は、GenAI・Agentic
AIをアプリケーション単位で運用的に統治し、リスクを事前に管理しながら価値を引き出す必要性を示している。

Gartnerの2026-04-28公開プレスリリース「Gartner Identifies Six Steps to
Manage AI Agent
Sprawl」では、エージェントの拡散を抑えるための方向性として、次の6点が示されている。

1.  エージェントガバナンスとポリシーの確立
2.  エージェントの中央インベントリ
3.  エージェントのID・権限・ライフサイクル管理
4.  AI情報ガバナンス
5.  エージェント動作の監視と是正
6.  責任あるAI利用の文化・教育

また、Gartnerの公開記事「AI Governance Requires More Than
Policies」（2026-06-10）は、ポリシーだけでなく、継続的な監視・検証・技術的な強制を組み合わせる方向性を示している。

### 3.2 本設計への適用

  ------------------------------------------------------------------------------------------------------------
  Gartner公開知見                     Copilotガバナンスへの適用
  ----------------------------------- ------------------------------------------------------------------------
  AI／Agentポリシー                   利用可能機能、禁止事項、承認基準、例外手続きを定義

  エージェントのインベントリ          利用可能なCopilot機能、MCP、プラグイン、カスタムAgent、所有者を台帳化

  ID・権限・ライフサイクル            ユーザーID、GitHub App、MCP接続先、最小権限、棚卸し、廃止を管理

  AI情報ガバナンス                    Private
                                      repoのアクセス権、機密ファイル除外、データ分類、プロンプトへの入力制限

  動作監視                            Enterprise audit log、SIEM、GitHub上のAgent activity、利用・コスト指標

  教育・文化                          利用者ガイドライン、レビュアー教育、管理者Runbook、事例共有

  技術的な強制                        Enterprise／Org Policies、managed settings、Rulesets、Actions／Code
                                      Security設定
  ------------------------------------------------------------------------------------------------------------

**設計上の結論**:
Copilotガバナンスは「規程を作る」だけでなく、「機能の許可・権限・データ・成果物・ログ」を技術的に統制する運用モデルにする。

## 5. AIガバナンス対象とリスク評価

### 5.1 管理対象

Copilotを構成する対象を、次の単位で台帳管理する。

1.  **利用者**: 社員、委託先、管理者、ライセンス保有者
2.  **機能**: Code Completion、Chat、Agent、CLI、Copilot app、cloud
    agent、Code Review
3.  **モデル**: 利用可能モデル、Previewモデル、モデル切替ポリシー
4.  **データ**:
    ソースコード、設計書、Issue、PR、ログ、秘密情報、個人情報
5.  **拡張・接続先**: MCPサーバー、Plugin、Marketplace、GitHub
    App、外部API
6.  **権限**:
    GitHubユーザー権限、Token、Agentのツール実行権限、リポジトリアクセス
7.  **成果物**: AI生成コード、テスト、ドキュメント、設定、PR
8.  **運用証跡**: 設定変更、ライセンス、Agent
    activity、利用状況、例外、インシデント

### 5.2 リスク評価の軸

  -----------------------------------------------------------------------------------------------------
  リスク領域              評価観点                               主なリスク
  ----------------------- -------------------------------------- --------------------------------------
  情報漏えい              入力データ、出力、外部送信、権限境界   機密情報・個人情報・秘密情報の漏えい

  セキュリティ品質        生成コード、依存関係、設定、脆弱性     脆弱性・バックドア・危険な設定の混入

  Agentの自律性           実行可能な操作、承認、権限             無承認の変更・削除・外部送信

  サプライチェーン        MCP、Plugin、Action、依存パッケージ    悪意ある拡張・改ざん・侵害

  正確性・品質            ハルシネーション、仕様整合性、テスト   誤実装・不具合・誤った技術判断

  知的財産・ライセンス    生成コードの出所、ライセンス、著作権   不適切なコード利用・ライセンス違反

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------
  区分                    例                                                                                        利用方針
  ----------------------- ----------------------------------------------------------------------------------------- ------------------------------------------------

### 6.3 Enterprise／Organization／Repositoryの責任分界

-   **Enterprise**:
    全社の最低基準、利用可能機能、モデル、共通MCP、Private-only、管理者権限、監査。
-   **Organization**: 部門別の追加制限、Copilot
    seat、対象Repo、例外、Code Security適用。
-   **Repository**: データ分類、Content
    Exclusion、Rulesets適用状況、Instructions、CI/CD。
-   **利用者**:
    入力情報の判断、生成物の検証、レビュー依頼、禁止行為の遵守。

Enterpriseで全社最低基準を強制し、Organizationはその基準を緩和できない設計を基本とする。

### 7.2 Enterprise managed settings

GHECでは、選択したOrganizationの`.github-private`リポジトリに`copilot/managed-settings.json`を配置し、Copilotクライアントに共通の管理設定を配布できる。2026年7月に一般提供となり、同年7月末にはCopilot
app／cloud agentへの適用拡張が発表され、8月にはMCP
allowlistが追加された。

**配置**

``` text
.github-private/
└── copilot/
    └── managed-settings.json
```

**設定例（初期検討用。実際のスキーマ・対応クライアントを確認してから適用）**

``` json
{
  "permissions": {
    "disableBypassPermissionsMode": "disable"
  },
  "allowedMcpServers": [],
  "deniedMcpServers": [],
  "strictKnownMarketplaces": true,
  "features": {
    "computerUse": false
  }
}
```

注意事項: -
上記は設計例であり、すべてのキーが全クライアントで同じように有効になることを意味しない。 -
`allowedMcpServers: []`の意味や空配列時の挙動は、導入時点のスキーマで検証する。MCPを利用しない方針なら、MCP機能自体のEnterprise
Policyも併用する。 -
`strictKnownMarketplaces`は許可Marketplaceの明示が必要になる場合がある。許可先の登録・動作確認を行う。 -
`features.computerUse`、`permissions.*`等は対応クライアントを確認する。 -
`permissions.allow`は広く設定しない。`ask`／`deny`を優先し、必要最小限の例外だけを許可する。 -
`model`を固定する場合、利用可能モデル・廃止・更新の運用が必要。 -
`.github-private`への書き込み権限は管理者・限定された運用担当者のみとし、変更はPull
Request・レビュー・監査対象にする。 -
設定変更の反映タイミング・キャッシュ・クライアント差異を検証する。

**管理対象の候補** - `permissions.disableBypassPermissionsMode` -
`permissions.disableAssistedPermissionsMode` -
`permissions.defaultMode` -
`permissions.ask`／`permissions.deny`／`permissions.allow` -
`enabledPlugins` - `extraKnownMarketplaces` -
`strictKnownMarketplaces` - `allowedMcpServers`／`deniedMcpServers` -
`features.computerUse` - `model` -
`telemetry.*`（必要に応じ端末管理・OpenTelemetryと組み合わせる）

※キーの追加・名称・対応クライアントは変更される。必ずGitHub公式のEnterprise
managed settings referenceを参照する。

### 7.3 MCPサーバー・Plugin・Marketplace

**基本方針: Default deny／Allowlist**

  ---------------------------------------------------------------------------------------------------------------
  項目                    初期方針                       承認条件
  ----------------------- ------------------------------ --------------------------------------------------------
  MCPサーバー             原則利用不可                   業務目的、データフロー、権限、提供元、ログ、脆弱性評価

  社内MCP                 セキュリティ審査後に限定許可   認証、最小権限、通信先、監査、保守責任者

  外部MCP                 原則禁止                       契約・プライバシー・データ保護・供給元審査

  Plugin                  承認済みのみ                   機能、権限、更新、依存関係、運用主体

  Marketplace             承認済みのみ                   公開元、署名・配布経路、更新方針
  ---------------------------------------------------------------------------------------------------------------

審査時には次を確認する。 -
MCP／Pluginが読み取り・書き込み・削除・外部送信のどの操作を行えるか -
ユーザー権限とAgent権限がどう連動するか - Token／OAuth scopeが最小か -
入力データや結果がどこに送られ、保存されるか - Prompt
Injectionを受けた場合の影響範囲 -
監査ログ・障害連絡・脆弱性対応の責任者 - 廃止時の無効化手順

`serverName`だけをセキュリティ識別子として信頼しない。可能な場合はURLや実行コマンド等、より確実な識別条件を用いる。許可リスト・拒否リストの挙動は公式仕様で検証する。

### 7.4 Content Exclusion

Copilotが特定ファイルにアクセス・参照することを抑止するため、EnterpriseレベルのContent
Exclusionを設定する。

対象候補: - 秘密鍵・証明書・秘密情報ファイル -
`.env`、credential、token、password等を含むファイル -
個人情報・顧客データのサンプル - 本番設定・本番接続情報 -
規制対象データ - 特定の機密設計・契約・脆弱性情報

ただし、**Content
Exclusionはファイルシステムのアクセス制御ではなく、完全な漏えい防止策ではない**。IDEから間接的に渡される情報、外部MCP、未対応クライアント等の制約がある。OS／リポジトリ権限、Secret管理、データマスキングを必ず併用する。

### 7.5 Private Repositoryのみ利用可能とする統制

一般ユーザーにPublic Repositoryを作成させないため、次を設定する。

1.  Enterprise repository management
    policyで、Organization内のRepo作成権限を制限する。
2.  OrganizationのMember
    privilegesで、メンバーが作成できるRepoをPrivateのみにする（必要に応じInternalも禁止）。
3.  Organization
    Owner以外の作成権限を制限する場合は、申請・承認方式を設ける。
4.  既存RepoのVisibility変更（PrivateからPublic等）を別のポリシーで禁止する。
5.  Organization外の個人所有Repoへのコード複製・Pushを禁止する運用を定める。
6.  外部コラボレーター、GitHub App、Deploy
    key、Tokenの権限を棚卸しする。
7.  Enterprise配下Organization外にユーザーがRepoを作れる構成が残っていないか確認する。EMU採用時はユーザー所有Repo等の制御も設計する。

**注意**:
Repo作成時のPrivate-only制限だけでは、既存RepoのVisibility変更を防止できない。作成制御と可視性変更制御を別々にテストする。

### 7.6 管理者権限・職務分掌

管理者を数名に限定する方針は適切。ただし、日常運用を一人に集中させず、最小権限と承認を分離する。

  ------------------------------------------------------------------------------------------
  ロール                              権限・責務
  ----------------------------------- ------------------------------------------------------
  Enterprise Owner                    Enterprise設定・全体ポリシー・緊急対応。必要最小人数

  AI Governance Manager               AI Controls、モデル・機能・MCP審査、利用台帳

  Organization Owner                  担当Orgの利用者・Repo・Org設定

  Security Administrator              Code Security、Secret、脆弱性対応、SIEM

  Repository Admin                    Repo固有設定・Content Exclusion・Rulesetsの運用

  Developer                           Copilot利用、生成物検証、PR提出

  Reviewer／Code Owner                設計・コード・セキュリティのレビュー

  Auditor                             ログ・設定・例外の参照（変更権限なし）
  ------------------------------------------------------------------------------------------

-   Enterprise Ownerは日常作業用アカウントと分離できる場合は分離する。
-   管理者アカウントはMFA／SSO等の認証統制を適用する。
-   管理権限の付与・剥奪は申請・承認・定期棚卸しの対象とする。
-   AI
    Controlsの変更権限を持つユーザーを限定し、監査ログで変更を追跡する。

## 8. 開発プロセス・DevSecOpsとの統合

### 8.1 AI生成コードの標準プロセス

``` text
要件・設計
   ↓
Copilotによる調査・設計補助
   ↓
開発者による生成コードの確認・修正
   ↓
ローカルテスト／静的解析
   ↓
Pull Request作成
   ↓
人間レビュー（Code Owner／必要な承認者）
   ↓
CI/CD・セキュリティチェック
   ↓
マージ・リリース承認
   ↓
運用監視・脆弱性対応
```

Copilotは開発者を補助するが、設計責任・コード品質責任・リリース責任を引き受けない。

  機能・統制                  推奨実装                                理由

  main保護・レビュー必須      Rulesets                                開発プロセス上の強制

  Secret Scanning／Push       GitHub Code Security設定                早期検知・防止
  Protection                                                          

  CodeQL                      Code Security Configuration             SAST

**原則**:
「強制・統制」はGitHubネイティブ設定、「実行ロジック・検査」はDevSecOpsテンプレート、「開発時の補助」はInstructions／ガイドラインに配置する。テンプレートにCopilot利用の検知や必須化を実装しない。

### 8.3 Rulesetsの推奨

-   Default branchへの直接Pushを禁止
-   Pull Request必須
-   最低レビュー数を設定
-   Code Ownerレビューを必要とする領域を定義
-   Required status checksを設定
-   Force push／Branch deletionを制限
-   必要に応じ署名済みCommitを要求
-   マージ方式・Linear history等を標準化
-   管理者Bypassは限定し、利用時に監査する

AI生成コードであっても、通常コードと同じ、またはリスクに応じて強化したレビュー・検査を通す。

### 8.4 Actions／CI/CDの統制

-   利用可能なActionsを許可リスト化する。
-   外部Actionは可能な限り完全なCommit SHAで固定する。
-   Workflowの`permissions`は最小権限とする。
-   `pull_request_target`等の危険なイベント利用を審査する。
-   Secretsをログ・Artifacts・生成プロンプトへ出力しない。
-   本番デプロイはEnvironment protection rules／承認を適用する。
-   AIがWorkflowを生成・変更した場合も、Workflow自体をレビュー対象とする。
-   Copilotに本番資格情報や長期Tokenを渡さない。

### 8.5 Copilot Instructionsの3層モデル

  ----------------------------------------------------------------------------------------------------------------------------
  層                      ファイル／設定                      記載する内容
  ----------------------- ----------------------------------- ----------------------------------------------------------------
  Enterprise              Managed settings                    クライアントの強制可能な設定、権限、拡張の許可・禁止

  Organization            Organization custom instructions    全社／部門共通の設計原則、言語、セキュリティ、レビュー方針

  Repository              `.github/copilot-instructions.md`   言語・フレームワーク・ディレクトリ構成・テスト方法・固有ルール
  ----------------------------------------------------------------------------------------------------------------------------

Instructionsは回答品質の補助であり、アクセス制御・秘密情報保護・レビュー必須化を実現する機能ではない。

**Organization Instructions例** -
既存の設計・コーディング規約を優先する。 -
不明な仕様・APIを推測で断定せず、確認事項として示す。 -
秘密情報・個人情報・顧客データを回答やサンプルに含めない。 -
生成コードに対してテストケースと検証観点を提示する。 -
認証・認可・暗号・入力検証・ログ出力に関する変更はリスクを明記する。 -
依存パッケージ追加時は目的・保守状況・ライセンス・脆弱性を確認する。 -
本番環境への操作やデプロイは人間の承認を要求する。 -
セキュリティ検査や人間レビューを省略しない。

## 9. 利用ガイドライン（利用者向け文書のドラフト）

### 9.1 利用目的

GitHub
Copilotは、コード理解、設計検討、実装補助、テスト作成、ドキュメント作成、リファクタリング等の生産性向上を目的として利用する。Copilotの出力は誤りを含む可能性があるため、利用者が正確性・安全性・ライセンス適合性を確認する。

### 9.2 入力してはいけない情報

以下は原則として入力しない。 - パスワード、API Key、Access
Token、秘密鍵、証明書秘密鍵 - 本番環境の接続情報・資格情報 -
不要な個人情報・顧客情報・決済情報 -
契約・規制・社内規程で外部AIサービスへの入力が禁止された情報 -
他社・顧客から預かった情報で、AI利用の許諾が確認できないもの - Content
Exclusion対象の情報

Private
Repositoryであっても、入力可能なデータが無制限になるわけではない。

### 9.3 出力の確認義務

利用者は次を確認する。 - 仕様・要件・設計との整合性 -
コンパイル・実行・テスト結果 -
認証、認可、入力検証、暗号、ログ、エラー処理 -
依存パッケージの安全性・ライセンス - 既存コードとの整合性・保守性 -
生成コードの出所・著作権・ライセンス上の懸念 -
不要なファイル変更・秘密情報・危険なコマンドがないこと

### 9.4 Agent利用時の追加ルール

-   Agentが提案する操作対象・変更範囲を確認する。
-   ファイル削除、外部通信、権限変更、依存追加、Workflow変更等は特に慎重に扱う。
-   不明なMCP・Plugin・Marketplaceを接続しない。
-   承認ダイアログを内容確認なしに許可しない。
-   `Allow all`／Bypass等の承認回避モードを使用しない。
-   Agentの変更は差分を確認し、PRでレビューを受ける。
-   本番環境への直接操作・デプロイを行わない。

### 9.5 禁止事項

-   Copilotを使ってアクセス権限のない情報を取得・推測すること
-   秘密情報・個人情報・顧客データを不適切に入力すること
-   AI生成結果を無検証で本番利用すること
-   セキュリティ検査・レビュー・承認を省略すること
-   未承認MCP／Plugin／外部サービスを接続すること
-   AIを使ってマルウェア、認証回避、不正アクセス等を実装すること
-   Copilotの出力を根拠なく正しいとみなし、説明責任を放棄すること
-   会社管理外のPublic Repoや個人アカウントへソースコードを複製すること

## 10. 監査・ログ・モニタリング

### 10.1 GitHub監査ログの利用

Enterprise audit logで確認する主な対象: -
Copilotプラン・ポリシー・設定の変更 - ライセンスの付与・剥奪 -
GitHub上のAgent activity - AI
Controlsや管理設定に関する変更イベント（利用可能なイベントを確認）

**制約**: GitHub Enterprise audit
logは、ローカルIDEで利用者が入力したすべてのCopilotプロンプトや会話内容を記録するものではない。GitHub公式ドキュメントは、ローカルセッションデータについて別の仕組みが必要であることを明記している。したがって「監査ログがあるから全プロンプトを追跡できる」と説明してはならない。

### 10.2 SIEM連携

-   Enterprise audit logをSIEMへStreamingする。
-   監査ログの標準保存期間（現行仕様では180日）を確認し、長期保存要件に合わせてSIEM側で保管する。
-   管理者権限変更、AI機能の有効化、MCP許可リスト変更、ライセンス大量付与、Repo
    Visibility変更等をアラート化する。
-   Copilot利用ログ・クライアントイベントを別途収集する場合、取得範囲・目的・本人通知・アクセス権・保存期間を法務／プライバシー部門と合意する。
-   プロンプト全文の収集は、必要性とプライバシー影響を評価し、デフォルトで収集しない方針を検討する。

## 11. インシデント・例外管理

### 11.1 インシデント例

-   Copilotへの秘密情報・個人情報の入力
-   AI生成コードに重大な脆弱性が混入
-   Agentが意図しないファイル変更・削除・外部送信を実施
-   未承認MCP／Pluginの利用
-   Public Repoへの誤公開
-   Copilot設定の不正変更・ポリシー逸脱
-   AI生成物に起因するライセンス・知的財産上の問題

### 11.2 初動対応

1.  影響範囲（ユーザー、Repo、データ、MCP、Token、生成物）を特定する。
2.  必要に応じCopilot機能・Agent・MCP・Token・GitHub
    App等を停止・失効する。
3.  Repo・ブランチ・PR・Actions・監査ログを保全する。
4.  秘密情報が含まれる場合はSecretのローテーション・失効を実施する。
5.  生成コード・依存関係・Workflowを検査し、必要に応じロールバックする。
6.  Security、AI Governance、法務、プライバシー部門へ連携する。
7.  原因・影響・再発防止策を記録し、ポリシー・教育・技術設定へ反映する。

### 11.3 例外申請

例外は、対象者・Organization・Repo・機能・データ・期間・業務目的・代替策・リスク・承認者を記録する。

-   期限付きとし、自動または定期的に失効確認する。
-   MCP／Pluginは提供元・権限・通信先・データ処理を必須評価とする。
-   本番直接操作・秘密情報アクセス・レビュー免除は原則認めない。
-   例外を恒久化する場合は、標準ポリシー改訂の要否を審査する。

## 15. 5,000ユーザー／5,000リポジトリでの運用設計上の留意点

### 15.1 5,000 Repoを個別管理しない

-   Enterpriseレベルの共通ポリシーを最大限活用する。
-   Organization単位で業務・規制・データ区分を整理する。
-   RepoはCode Security
    Configuration、Rulesets、テンプレート、検索・棚卸しで標準化する。
-   例外Repoだけを個別管理する。
-   Repoの作成・移管・アーカイブ・Visibility変更を台帳と連動させる。

### 15.2 監査・設定ドリフト対策

-   Enterprise／Organization設定を定期的にエクスポートまたはAPIで棚卸しする。
-   `.github-private`の変更はPull Request経由に限定する。
-   変更前後の設定をバージョン管理する。
-   重要設定の変更をSIEMで検知する。
-   管理者が数名であっても、設定変更者と承認者を可能な範囲で分ける。
-   GitHubのUI/APIの変更に合わせて設定確認手順を更新する。

### 15.3 Organizationの分割基準

Organizationは単純な人数だけで分けず、次の差異を考慮する。 -
データ分類・規制要件 - 開発言語・開発基盤 - 本番環境の重要度 -
Agent／MCPの利用要件 - 外部委託先・外部コラボレーターの有無 -
ライセンス・コスト管理単位

ただし、Organizationを細分化しすぎるとポリシー管理・監査・運用負荷が増える。全社共通設定をEnterpriseに置き、差異が必要な領域だけOrganizationで分ける。

## 16. 最終推奨事項・優先順位

### 最優先（導入前に必須）

1.  Enterprise AI
    ControlsでCopilot機能・モデル・新機能の利用を明示的に管理する。
2.  一般ユーザーのRepo作成・Visibility変更をPrivate-onlyに統制する。
3.  `.github-private/copilot/managed-settings.json`を中央管理し、Agentの権限回避・未承認MCP／Pluginを抑制する。
4.  Content Exclusionを設定する。ただしアクセス制御の代替にはしない。
5.  Rulesets、Secret Scanning、Push Protection、CodeQL、Dependency
    Review等を適用する。
6.  Audit logをSIEMへStreamingし、ログの取得範囲と限界を明文化する。
7.  Copilot利用ガイドラインとAI生成コードレビュー基準を公開する。

### 次点（Pilotで検証してから展開）

1.  Copilot Agent／cloud agent／Code Reviewの段階導入
2.  審査済みMCP／Pluginの許可
3.  Organization instructionsとRepository instructionsの標準化
4.  KPI／KRIダッシュボードと費用対効果分析
5.  利用者教育・管理者Runbookの定着

### 原則禁止または個別審査

-   未承認MCP／Plugin／Marketplace
-   Bypass／Allow all等の承認回避
-   Agentによる本番環境への直接変更・デプロイ
-   秘密情報・顧客情報・個人情報の無条件入力
-   Copilot出力だけを根拠とするセキュリティ承認
-   人間レビューやCI/CD検査の省略
